## 关键经验

### 页面形态可以不同，不必强行统一

视频本土化是工具型工作台（视频预览 + 时间轴 + 任务面板），其余页面是列表型管理页。它的顶部显示当前项目名而非页面标题，也没有搜索框——这些是用途决定的，不是不一致。判断框架是否统一时，先区分“同一控件的两种实现”与“不同用途的两种布局”。

### 前端

- **不要用浮点数做哈希混合。** `seed * 2654435761 + hash` 会超过双精度上限（2^53），低位被吞掉，随机排序退化成固定顺序。用 `Math.imul` 配合异或做 32 位整数运算。
- **同一元素只留一份实现。** 搜索框曾被四个页面各写一遍，值已经漂移（间距 6/8px、圆角 6/7px、高度 28/30/32/34px）。统一的做法是提到 `app.css`，差异用修饰符表达（如 `.compact`）。
- **组件内联样式有作用域隔离，`@import` 的样式没有。** 实测：内联规则编译后带 `.svelte-xxxxxx` 后缀，而 `<style>@import './+page.css';</style>` 引入的类名是裸的、全局生效，且不会触发未使用样式警告。三种写法里 `<style src="...">` 在 Svelte 5 无效（样式会被丢弃）。因此拆样式到独立文件是可接受的权衡（避免主文件过长），但必须先接受失去隔离，并在命名上自律。
- **模板里挂着的类名未必有样式。** 用脚本比对「模板出现的 class」与「CSS 定义的 class」可以一次找出全部死类名，比逐个 grep 可靠。静态 `class="..."` 与动态 `class:xxx={...}` 需要分别扫。

### 验证手法

- **要验证会写用户数据的操作时，用 Playwright 路由拦截返回假响应。** 请求、成功回调、界面更新都会真实走一遍，但数据不会被改动。批量删除、批量 ASR、单个情绪识别都用这个方法验过。
- **拦截请求还能区分新旧代码是否生效。** 例如「删除一个不存在的文件」在修复前会弹窗、修复后直接放行，行为差异本身就是证据。
- **浏览器自动化优先用项目自带的 Playwright 起独立实例**（`npx playwright`，系统 Chrome 通过 `channel: 'chrome'`）。`ego-browser` 是与人共用同一个浏览器，一旦有人在窗口里操作，自动化就会被暂停。

### 本机工具

- `~/.pi/agent/extensions/safety-gate.ts` 会把危险的 `rm` 改道为移入废纸篓。它曾经把命令里的 `2>/dev/null` 当成删除目标，导致弹窗后报「找不到目标」；现在重定向会被过滤，且目标全部不存在时不再打扰。
- 该扩展目录已用 git 管理。改动扩展后应在该目录提交，不要再手工留备份。

## 协作偏好

- **说人话**：先给结论，再讲原因。用户不熟悉的术语要顺手解释，配一个具体场景（谁在什么页面做什么 → 系统怎么处理 → 最后看到什么）。不重要的内容一句话带过，不要所有事都展开。
- **给判断，不甩选项**：有明确推荐就直接说，附上理由和影响。
- **改动要能验证**：不能只说「已改好」，要说清验证了什么、还有什么没验。
- **减少重复**：相同元素用一段代码加参数，不要每个页面各写一套。框架统一优先于局部微调。
- **开源视角**：任何改动都要考虑会不会把私人内容、本机路径或临时产物带进仓库。
- 用户会逐页推进，一页做完验收后再进入下一页；发现新分支时先问一个最关键的问题。

## 开发环境

- 完整启动：仓库根目录 `./start.sh`；前端 `frontend/` 用 pnpm，后端用仓库 `.venv`。
- 正式数据目录固定为 `VOICE_STUDIO_DATA_DIR`（默认 `~/VoiceStudio`）。测试、验收和浏览器回归一律使用本次运行独占的临时数据根目录，不写用户正式数据。
